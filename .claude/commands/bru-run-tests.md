---
description: Run Bruno tests for a collection, folder, or individual request
argument-hint: [path: collection / folder / request file, or leave blank to choose]
---

Run Bruno tests using the `bru run` CLI against a collection generated by this repo. Handle individual requests, tag-group folders, or whole collections, with optional data-driven CSV/JSON iteration and an HTML/JSON report.

## Input

Path argument: `$ARGUMENTS`

Interpret `$ARGUMENTS` as one of:

| Shape | Example | Scope |
|---|---|---|
| Empty | `` | Ask the user — list folders under `Bruno Collections/` and let them pick |
| Collection folder | `Fraud Evaluation (v13.0.0)` | Run **all** requests in that collection |
| Tag folder (path inside collection) | `Fraud Evaluation (v13.0.0)/CR_-_FraudEvaluationAssessment` | Run only requests in that folder |
| Single request | `Fraud Evaluation (v13.0.0)/CR_-_FraudEvaluationAssessment/EvCR Start...yml` | Run that one request |

Paths are relative to `Bruno Collections/`. Accept the path with or without the `Bruno Collections/` prefix.

## Pre-flight checks

1. Verify `bru` CLI is on PATH: `bru --version`. If missing, tell the user to install `@usebruno/cli` and stop.
2. Resolve the target collection root (the folder containing `opencollection.yml`). All `bru run` invocations must `cd` into the collection root, since paths inside the collection are resolved relative to it.
3. List the available environments: read filenames in `environments/*.yml`. If only one exists, use it as the default; otherwise ask the user which to use.
4. If the scope is the collection root or a folder, check whether a `data/` directory exists. If it does, ask whether the user wants a data-driven run (and which file).

## Ask the user (only what isn't already obvious)

Use a single `AskUserQuestion` call to gather:

- **Environment** — only if `environments/` has more than one file.
- **Data file** — only if a `data/` directory exists AND the user hasn't already specified one in `$ARGUMENTS`. Offer: none / pick CSV / pick JSON.
- **Reporter** — HTML (default), JSON, both, or none.
- **Stop on first failure** — yes / no (default no, so iteration coverage is visible).

Skip any question whose answer is unambiguous from context. Do not ask questions whose answer the user has clearly already provided.

## Run

Build the `bru run` invocation from inside the collection root:

```bash
cd "Bruno Collections/<collection folder>"
bru run "<scope path relative to collection root, or omit for full collection>" \
  --env "<environment name without .yml>" \
  [ --csv-file-path "./data/<file>.csv"  |  --json-file-path "./data/<file>.json" ] \
  [ --reporter-html results.html ] \
  [ --reporter-json results.json ] \
  [ --bail ]
```

**Bruno CLI flag notes (current versions):**
- Data files: `--csv-file-path` and `--json-file-path` (not the older `--data`).
- Report flags: `--reporter-html <file>`, `--reporter-json <file>` — can be combined.
- `--iteration-count N` repeats the whole run N times; useful for soak testing but unrelated to `--csv-file-path` (which iterates over rows).
- `--env-var key=value` overrides individual env vars at the command line (e.g., for injecting an ID into `fraudevaluationid` without editing the env file).

Run the command and stream its output. Do not background it — the user wants to see results.

## Report

After the run, summarise:

- Total iterations / requests / assertions, with pass/fail counts.
- The path to the report file(s) (absolute, so the user can open them directly).
- Any iteration that failed every assertion — flag this as likely a server/network issue rather than a test-logic issue.
- If all iterations returned the same non-2xx status with empty bodies, suggest checking the env's `baseUrl` independently (e.g., a one-shot `curl -i`) before assuming the tests are wrong.

## Constraints

- Do not modify request files, env files, or fixtures as part of running tests. If a test fails because a path param env var is empty, surface the issue and stop — do not silently populate it.
- Do not commit `results.html` / `results.json` — they're per-run artefacts and belong in `.gitignore`. Mention this if you notice they aren't already ignored.
- If a data file is specified but the scope is more than one request, warn the user: data-driven iteration applies per-request, so a folder run with a CSV iterates *every* request in the folder N times — usually not what's intended unless every request consumes the same columns.
